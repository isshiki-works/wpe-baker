# WPE Baker 技术记录

中文（本文） ｜ [English](technical-notes.md)

> 这是开发过程中的技术记录，面向想了解实现细节与逐案数据的开发者。使用说明请看[首页 README](../README.zh-CN.md)。

Windows 离线 Scene 壁纸烘焙器。1.0 只面向**重型** Scene 壁纸：渲染负担确实重、且有大量可预计算内容；已经很省的、或者主要靠实时交互的作品按设计跳过。这个目标窄，但并不罕见：本机 113 案全部按原作实测，61 案（54%）核显域功耗 ≥3 W，31 案不到 1 W。C# / WPF 界面和命令行共用一条流程：分析 Scene、生成视频、保留必要实时层，产出独立 Wallpaper Engine 项目。普通用户无需 Python、编译环境或云服务。

本地版本支持自动图层分配和逐个成品验证，兼容范围由场景结构、实时依赖和实际循环决定。单个样本成功、代码检查或打包完成都不代表任意壁纸可以省电。

**工具会在渲染任何东西之前告诉你这张值不值得烘。**大约一半的 Scene 壁纸是值得烘的对象：本机 113 案壁纸逐案按原作在笔记本核显上实测（60 fps），61 案（54%）核显域功耗 ≥3 W，其中 17 案能烘成整幅视频。另一头同样真实：31 案原作不到 1 W，给这类烘一份成品，花掉的是磁盘和烘焙时间，换不回功耗（见「重型与轻型」）。平台能读到功耗计数器时，工具会先在官方播放器里播原作实测一次，如实报出读数，原作本来就轻就直接告诉你不用烘。

目前有实测省电证据的全是重型壁纸：按笔记本自己的屏幕分辨率重烘后，亚托莉、百合、绫波丽、雷欧的核显域功耗降 49–96%、封装功耗降 17–60%（随作品与帧率不同，逐案见「功耗」）。

**适用范围。**适合画面为主、带周期动画的场景壁纸；重交互作品（眼动、昼夜切换、视差、自定义面板）本版不会有收益，工具会在渲染之前直接告知：本机库里订阅量前 30 的作品，实测的 7 个成品没有一个省电。音频响应保留实时，不影响生成。

**“值不值得烘”是两步，不是一步**：第一步看原作功耗——核显域 60 fps 下 ≥3 W 才有可省之物；第二步看路线——省电来自**把整层整幅烘成一段视频**（上面四案核显域降 70–96% 都是这条路线）。只把图层效果链的**前缀**烘成视频、图层本身仍然实时跑的「效果前缀」路线，只有在被烘走的那一段占工作量大头时才省得下来（雷欧 −73% 就是这种），本轮 5 个重型 effect_prefix 案核显域只落在 +0.3% ~ −15% 之间，**不算省电**。所以工具对 effect_prefix 路线的结论会带一句“这条路线省电有限，除非被烘走的部分占大头”，两个条件都满足才承诺省电。

## 开始之前（第一次用请先读这 1 分钟）

**你需要有什么**：Windows 10/11 64 位；已安装 Wallpaper Engine（Steam 版）并已订阅你想烘的那张壁纸；一块支持 Vulkan 的显卡。Steam 和 Wallpaper Engine 都不需要开着——开着的话程序能直接读到你当前屏幕上的壁纸，没开就退回读 Steam 的安装记录。完全没装 Wallpaper Engine 时程序仍能启动，但分析要靠它的 assets 目录读着色器和特效，所以实际用不了；同时也没有播放预览和功耗实测。

**你不需要装什么**：不用装 .NET（运行库已经打包在这个文件夹里），不用装 Python、编译环境或 FFmpeg，也不用联网。

**三步开始**：

1. 把压缩包**整个**解压到一个你有写入权限的目录（例如 `D:\WpeBaker`）。不要放进 `C:\Program Files`，也不要直接在压缩软件窗口里双击运行——程序要读同目录下的 `renderer\`、`encoder\`、`tools.json`，缺一个都起不来（缺件时程序会直接告诉你缺的是哪一个、在哪个路径）。
2. 双击 **`WpeBaker.exe`**（图形界面，绝大多数人用这个）。同目录下的 `wpe-baker.exe` 是命令行版本，双击只会一闪而过，它是给脚本和批量处理用的。
3. 第一次运行会弹出蓝色的 **“Windows 已保护你的电脑”**。本程序没有代码签名证书，这个提示只说明“没买签名”。点弹窗里的 **“更多信息”**，再点 **“仍要运行”**。也可以在解压前右键压缩包 →「属性」→ 勾选「解除锁定」→ 确定，再解压，这样就不会拦。

**先看一眼值不值得烘**：这个工具只对**重型** Scene 壁纸有意义。随机抽的 7 张里没有一张烘出来真省电，因为它们原本就只吃 0.09–1.1 W。分析阶段会先在官方播放器里实测你这张原作的功耗并直接告诉你结论，看到“烘了省不回来”就别烘了。

## 实测结果（成品为 RC6 包 2026-09-16 产出，功耗实测 2026-09-17，代码为 RC8 2026-09-17）

发布分支与提交、Baker.Core.Tests 通过项数、便携包与源码包的 sha256 与字节数，见包内 `build-records\` 与发布页的校验值清单。下文「RC8 之后的改动」列出的能力（三档预设、烘焙前实测原作功耗、帧率自动、取舍清单、编码器收窄、硬解标注）都在本次发布的集成分支上，2026-09-17 的 RC8 包早于它们，发行包必须从带这些改动的分支重新打包。下面四个成品由 RC6 包内 CLI 产出；RC8 代码在本机（RTX 5090）把四案的 analyze 与 bake 各重跑了一遍，route、组数、每组标志、候选数、选中周期帧数、起点帧、`loop_validation` 与 RC6 逐字段一致（`reports-20260916/regress-rc8-round2.md`）。**功耗没有重测**，下表仍是 RC6 成品在 2026-09-17 的实测值。

## 1.0.1 / 1.0.2 的改动（2026-09-18）

- **两个独立选项取代了一个预设。**动画精度（效率 5% / 平衡 3% / 质量求最小改动）只管调速预算，默认平衡，质量档可显式选择、上限 600 秒，结论行写明实际按哪一档生成（plan 的 `preset_applied`）；交互处理（保留 / 固定视角 / 关闭）只管鼠标、音频这类由输入驱动的内容，默认固定视角，关闭会另外去掉指针效果与采样成本高的大面积音频效果。时钟、日期、媒体文字、FPS、BGM 永远保留实时。
- **不再有静默兜底。**你的设置跑不通就报跑不通；只有另一组两轴设置实算通过时，plan 才写 `suggested_change`（中英一句话、设置、已验证、plan 路径），界面上一键按它重新分析。同一次分析里已验证可用的子方案直接采纳（Alone 默认设置下 4 组可生成）。
- **分层布局最多 4 个视频组**（2–4 组省电，6 组核显 +106%，9 组封装 +10.9%）。实时小组件默认置顶（`--live-overlays foreground`）。
- **分析缓存：**同一输出目录改设置重分析时复用场景加载与周期求解（3426865175 4K：4.98 s → 0.95 s）。
- **烘焙前实测原作功耗默认关**（`--measure-source`；界面里是可选勾选，约 60 秒）。
- **界面：**结论四态固定文本；"技术细节"折叠为纯数字表；"本次未包含"卡片只列实际未包含项；高级区有改动时显示"自定义"；兼容模式勾选等于 `--keep-live on`，完全走 1.0 的分析路径，plan 与 1.0 逐字节相同。
- **1.0.2：分析与生成共用一套准入判定。**循环分配判定（粒子平稳性、残差掩盖）在分析阶段执行，必须保留实时的子树在报告写"可以生成"之前就已确定。生成失败直接报失败，不再自动重渲染，手动重试可用。候选按帧数从短到长排序。阿米娅（3486806915）1080p 平衡档：RTX 5090 上 8 分 44 秒，接缝校验通过。
- 单测 1437 项。

## RC8 之后的改动（本次发布）

- **三档预设取代了循环取向。** 档位管的是"允许多大的观感改动"，循环长度是求解结果：`--preset efficiency|balanced|quality`（默认 balanced；质量档可显式选择，上限 600 秒，plan 的 `preset_applied` 记实际档位），效率档给每个可见分量 5% 的改动预算并在预算内取最短循环，平衡档 3%，质量档不给百分比、直接求改动最小的解。长度上限（600 / 600 / 1200 秒）只是兜底，不是旋钮；2 GiB 体积上限可能把它压得更短，plan 里写明最后是被哪一条限住的。三道护栏三档相同、不随预算变：最慢的可见项至少走 3 圈、循环至少 60 秒、任何可见项的峰值速度偏差不超过 0.2 px/s。27 案扫描下循环长度中位：效率 146 秒、平衡 200 秒、质量 483 秒。要看的量是一个循环内的相位偏移圈数而不是百分比——3% 档 120 秒循环偏 0.360 圈，5% 档只偏 0.116 圈。预算买到的是"改频率"：按我们看过的样片，改频率不容易看出来，改运动轨迹能看出来，所以位移淡化那条路三档都不用。
- **帧率不再固定默认 120，改成取"你的 Wallpaper Engine 帧率设置"与"屏幕刷新率"里较小的那个。** 依据是实测：原生分辨率下解一路 120 fps 视频，在核显上比画一张轻量壁纸还贵（7 案里 4 案成品封装功耗 +11%~+26%，一案 gfx +38%）。分辨率与帧率仍可手动改，plan 里逐项记来源（预设 / 自动 / 手动覆盖）。
- **烘焙前先实测原作功耗。** 平台能读到 RAPL 能量计数器时，`measure-official` 会在官方 Wallpaper Engine 里播原作、等稳定、采样 30–45 秒、把你原来的壁纸还原回去，并报出核显域与封装功耗读数。原作核显域本来就很低时，结论行直接说"烘了省不回来"，但要不要继续仍由你决定。给绝对判断需要真的有核显域计数器（Intel PP1 / GFX / GT）：只发布 PKG 与 CORE 的机器（我们的 AMD 台式机就是）报 `unsupported_platform`、不给判断，也不编数字。笔记本 Intel 核显上同一窗口与手工读数差 0.36%。这是对你这台机器的一次测量，不是对结果的承诺。
- **整幅被实时元素挡住时，报告列出"关掉什么能换到整幅视频"。** 一个图层要留实时，是因为循环之外有东西在喂它：鼠标、音频、系统时钟、媒体播放器、上一帧画面。分析把它们分成可取舍的（鼠标特效、音频律动、视差、时钟日期、一次性入场动画、媒体信息、自带 BGM）和不可取舍的（画面主体本身、相机与脚本类故障），再列出让这张变成整幅视频所需的最小一组取舍，逐项写明代价。113 案里允许这些取舍后，**分析层面**可解锁的整幅从 39 变 68；54 个候选案里 29 案只需关掉用户能接受的元素，其中 8 案只需关一项。**这 68 只是分析判定：把其中 23 案照清单真烘一遍，0 案烘出成品**（烘制阶段的循环分配把粒子系统与主体动画层改判实时，整幅不再成立）。**取舍功能因此标为实验性，结果一律以烘制阶段为准。****"变成整幅"不等于"零实时"**：按最小清单关，29 案里只有 1 案彻底没有实时层，12 案残留 1–3 层、5 案残留 10 层以上，所以清单会同时写明还剩什么在实时。视差默认保留；排除父层会连带子层（3659877246 关掉视差会把时钟、日期、星期一起带走），清单按结果 plan 里的实际排除集生成，写的是你真正会失去的东西。不列就不关。
- **成品编码的硬件通道收窄到厂商无关的一条**，见「裁减范围」：`nvenc / qsv / amf` 这几个档位已经去掉——包内 ffmpeg 白名单里本来就没有它们。
- **硬解短检写明在哪台机器、哪几张卡上验的**，并对多数核显解不动的尺寸给出提示，见「裁减范围」。
- **烘焙更快了**，同样输入、成品逐字节相同，见「烘焙耗时」。

## RC8 新增的判据与出口（2026-09-17）

九条分支一次性并入主线（`fix/silent-rejections`、`feat/single-shot-live`、`feat/layout-demotion`、`feat/no-candidate-reason`、`feat/shader-verdict-dedup`、`feat/video-shell`、`feat/messages-i18n`、`feat/video-control-scope`、`feat/sdr-closure`），测试从 402 涨到 557，未改 C++ 原生渲染器。这一批全部是判据与出口，没有放宽任何接缝或周期阈值，也没有为单张壁纸特判。

- **视频外壳判据默认拒绝**。六条纯结构判据同时成立时（路线是整层替换；周期分量非空且全部以 `video/` 开头；没有未解析的时间机制；候选不需要调速；那段视频由唯一一层不透明、整幅、居中的图层承载；被烘图层不含任何特效通道），说明烘出来的东西与原作结构同构——都是一次视频解码加一次全屏贴图，工作量不转移。这时 plan 写 `video_dominant.status=video_shell`，追加一条 blocker 并把 `status` 置 `requires_resolution`，bake 入口直接拒。要烘就在 **analyze** 阶段显式传 `--video-shell allow`（`bake` 子命令没有这个开关），plan 记 `override_accepted` 并保留与拒绝时逐字相同的 `evidence`。任何一条证据读不到就判 `not_video_shell` 放行，保守方向固定。理由里没有任何功耗数字：判的是结构，不是估算收益。
- **全幅布局的尾组降级**。全幅因视频组多于一个被拒时，唯一允许的自动补救是把"第一个不透明底组之后的全部视频 root"整体退回实时，保持原位、原父子变换、原绘制顺序、原视差深度。三条采纳条件全部满足才生效，任一不满足维持原拒绝、不做部分降级：退回后恰好一组且承担清屏、非透明、依赖闭包不额外拉走 root；被退回的可见可绘制层 `canvas_fraction` 之和小于保留组内的最大值（同类量比较，没有魔法常数）；退回后可见的实时 root 在 `source_allocation_order` 中严格递增。生效时重算循环，plan 记 `layout_admission_demotion`（含被退回的 root、层名、占比、保留组）与 `video_layout_admission.status = planned_layout_allowed_after_demotion`。不采纳时也把可执行的 `--retain-live <ids>` 写进冲突文案。
- **一次性动画轨判实时**。运行时观察里 `looping=false`、`playback_mode=single`、`confidence=high` 且机制不是视频的动画轨，其所属图层在分配阶段判实时（reason `single_shot_animation`）——循环视频会每周期重播一次本来只播一次的动画，而原作在时长之后不再跳变。置信度不够就不下结论，维持原有的 `loop.unresolved` 路径。
- **全幅不可达写明白**。唯一的视频组不承担清屏、它前面还有可见的实时绘制层、这些层又不能被前景提升搬走时，布局裁决记 `full_frame_unreachable` 并逐条点名是哪些层、为什么必须实时，不再给"改设置后重新分析"这种在该结构下无效的建议。没有任何视频组时记 `not_applicable_no_video_group`，也不再追加无效的布局指令。
- **无候选必须给结构化原因**。`loop.no_candidate_reason` 只在候选为空时非空，给出 kind（固定周期超出搜索上限 / 帧网格上没有满足全部分量的整帧 / 没有任何已建模的时间机制 / 视频调速取不到整数帧）、上限秒数、固定周期秒数，以及 shader 分量数、运行时动画周期数、运行时时钟 uniform 数三项计数供用户自己核对"到底是没运动，还是分析没看懂"。顶层新增 `suitability`：`verdict` 取 `suitable` / `requires_user_choice` / `unsupported_capture` / `not_suitable`，带规则名与中英理由；能力缺口与布局冲突只进 `notes`，不覆盖主裁定。
- **同一层同一 shader 只裁定一次**。方程规则链已经裁定过的 (图层, shader) 不再以运行时材质的名义重复报一条未解析项。旧口径按材质 role 白名单只挡 `effect`，同一个效果被运行时实例化成 `source` 与 `effect` 两份时就会把已经解析完的 shader 再报一次（绫华 3288381550 的假阳性即出自此处）。同时把残差掩盖需要的机制知识从文案里拿出来，改读结构化字段 `bounded_displacement` 与 `mechanism`。
- **脚本的视频控制按目标定界**。旧判据是"场景里任意一段脚本同时出现视频控制调用，就把每一条视频轨判为受控"，整场连坐。现在四条并列，命中任一才算受控：运行时对该层有非初始化的视频属性写入；含视频控制调用的脚本在运行时读到该层的 `videoTexture`；该层自身的脚本绑定含控制调用；目标解析不出来时（控制脚本 owner 在初始化阶段没有任何 `read videoTexture` 记录且自身不是视频轨）才退回全场景连坐。plan 记 `video_control_scope` 的 `resolved_targets` / `unknown_scope_owners` / `scene_wide_fallback`。另外粒子定义里 `audioprocessingmode ≠ 0` 的发射器/初始化器/算子直接判实时——音频是外部实时输入，输入驱动的层不进烘焙；粒子的非周期理由也具名化（湍流噪声场 / randomframe / 随机初始化器 / 发射盒范围 / 音频输入 / 定义读不出来 / 只是没建模），写进 `particle_nonperiodic_reason`。
- **HDR 改为逐层 SDR 辐射闭合证明**。`general.hdr` 这个标志本身不再是拒绝理由；改为对被捕获组内每个可见绘制层跑五条判据：材质封闭（shader 在已知的 flat / genericimage 系 / solidlayer 集合内、无作者 effects、combos 只允许 `VERSION`）、混合封闭（pass blending 与 `colorBlendMode` 在已知安全值内）、输入封闭（每个纹理的 `.tex` 前导必须是 8bit 无符号格式，视频包要求解码器 `pixel_format` 也是 8bit）、标量封闭（color / brightness / alpha 与被捕获的 `clearcolor` 必须是落在 [0,1] 的字面量，脚本或动画绑定一律判未知）、无反馈路径（组内不得读 `_rt_` 前缀的渲染目标）。五条全成立才 `hdr_radiance_closure.status=closed`，**任一未知即判不通过**，blocker 保留原句并在后面追加 `Unproven:` 点名是哪个组、哪个层、哪条判据。保守方向固定在"未知即拒绝"一侧：动画绑定的标量不猜关键帧极值，8bit 容器只认有据可查的那一个取值。
- **不再有零理由的退出**。`whole_layer.status=unavailable` 而 `whole_layer.blockers` 与 `loop.unresolved` 皆空时按内部错误直接报错（effect_prefix 路线带可用缓存时豁免）。`source_static` 判否时必须点名图层与机制，不再静默返回 false。analyze 自己也会把 README 早就承诺的循环分配回退走一遍并留证：`loop_allocation_fallback` 记下保留了哪些作者根、重新分析后的路线与候选数，能走通就在 `loop.unresolved` 里给出 `--retain-live <ids>` 这条出路，走不通写明原因；**analyze 不替用户改分配**。
- **入口分类与帮助**。预设包（有 `dependency`、没有 `file` 也没有 `type`）不再和真视频壁纸共用一句话：stderr 输出 `status=not_applicable`、`kind=preset` 与它依赖的作品 id，并以**退出码 3** 与视频壁纸的 1 区分；真视频 / 网页壁纸只陈述"本工具只处理 Scene"这个事实。`analyze --help` / `-h` 现在打印该子命令自己的用法并退出 0（此前会当成源路径去找文件而报错）。
- **中英文案表与一行结论**。新增 42 条文案 key（中英各一套），plan 并列输出 `blockers_localized`、`loop.unresolved_localized` 与顶层 `summary`（`verdict` 取 `bakeable` / `blocked` / `not_applicable` / `unknown`，附中英各一句结论）。CLI 新增 `--lang zh|en`（不传时按系统界面语言猜），analyze 结束时在 stderr 打一行对应语言的结论，stdout 仍是纯 JSON。`blockers` 数组与 `loop.unresolved[].detail` 里的历史英文**逐字未变**，下游按字符串匹配的脚本不受影响。界面语言在窗口右上角切换，默认跟随系统语言；这一版不记忆手动切换的结果，关掉重开会回到系统语言。命令行的 `--lang zh|en` 只管结论那一行。

| 轻型 <1 W | 31 | 12 | — | — | — |

中型与轻型两档只拆出了整幅可烘的案数；重型那一档的路线拆分是完整的（17 + 18 + 8 + 18 = 61）。

最重的三案是 26.4 / 25.0 / 22.8 W，都落在分层或保留实时路线上，不是整幅；能烘成整幅视频的最重一案是 14.2 W。

更早从同一批里随机抽的 7 案连成品一起测过（2026-09-18，7 案 × 60/120 fps，14 案次全部完成），没有一案有意义省电——但那 7 案里只有 1 案是重型（14%，全量是 54%），所以它说明不了总体省电率。它真正立住的是帧率与轻量壁纸这两条：

| 帧率 | 7 案的结果分布 |
|---|---|
| 60 fps | 5 案在测量噪声内，1 案比原作更费，1 案（重型、保留实时）核显 −3.7% 但封装 +12% |
| 120 fps | 4 案比原作更费（封装 +11%~+26%，其中一案 gfx +38%），3 案持平或在噪声内 |

其一，**原生分辨率下的 120 fps 不是白给的**：核显解一路 120 fps 视频比画一张轻量壁纸更贵，所以帧率默认改成取 WPE 帧率设置与屏幕刷新率里较小的那个，不再固定 120。其二，**"能烘"不等于"值得烘"**：那 7 案里六案原作核显域在 60 fps 下只有 0.09–1.1 W，没有可省之物；唯一重型那案（11.6 W）只能靠保留部分图层实时来烘，结果核显域降 3.7%、封装反而 +12%。所以要先实测原作功耗，也所以"保留图层实时"是一个带实测代价的取舍选项，而不是默认退路。

113 案的全量总账（2026-09-18 在本机 5090 上按本次发布的代码重跑，逐案表见 `reports-20260916/full113-rc11-bake.md`）：

- **分析判定可烘 84/113（74%）**：整幅 39、保留实时 27、分层 18（其中 6 案要按 plan 给出的源作者根建议补跑才回来）。
- **主队列 78 案全部烘完，其中 48 案烘出了带视频循环的成品（62%，合计约 1.9 GB）**；对 113 案总集是 **42%**（48/113）。其中 6 案来自第二轮：跑批脚本把 12 个保留实时路线的 1 帧结果当成了烘成，这 12 案按 `--video-layout layered` 重跑后 6 案出了视频循环（`reports-20260916/full113-rc11-layered12.md`）。要按源作者根建议补跑 analyze 才可烘的那 6 案也烘了，无一出循环（5 案无循环、1 案异常），不计入 78。
- 另有 **11 案的结果是静止画面（1 帧、没有视频文件）**，单独算一类：这类结果等于一张静态图配上全部实时元素，不要当成省电成品（例如 3715870843：分析给出 480 帧循环，烘制时那一组被判成画面不动，只出 1 帧）。本版起这类结果记为 `static_only`，不再与带视频循环的成品共用 `candidate_generated`。
- 失败 19 案：找不到循环 12、异常 2、超时 1（分层多组串行渲染）、接缝校验拒 1、合成拒 2、硬解拒 1。
- **换成本版随包的渲染器没有改变成品**：可比的 16 案成品 SHA256 全部一致、0 案不一致。
- 单槽跑完这 78 案总墙钟 9 665 s（其中约 1 070 s 在等另一个会话占着的锁），每帧 CLI 0.0162 s。

**能烘不等于能省。** 目前实测过的成品共 21 案（60 fps，在官方播放器里 ABBA 实测，逐案见 `reports-20260916/abba-heavy-rc11.md` 与 `abba-wholelayer-rc11.md`）：达到省电门槛——核显域功耗降 30% 以上、且封装功耗不升——的有 **7 案，三分之一**；只算原作 ≥3 W 的重型，是 19 案里 5 案。按路线看：整幅整层成品 5 案省 4；效果前缀成品 10 案省 3（亚托莉 −90%、雷欧 −73%、Lost Landscape −57%），这条路线只有被烘走的那部分占了工作量的大头才省得下来；保留实时与分层成品 8 案省 2，**其中 5 案比原作还费**（封装 +8% ~ +23%）——它们的 3D 负载几乎没动，又多了一路视频解码。9 个视频组的 3669680904 最差，封装 +10.9%。

7 个省电成品的去极值平均（去掉最好与最差）：**60 fps 核显域 −76.5%、封装 −29.9%**；120 fps 只有 4 案，核显域 −85.3%。7 案里 4 案按屏幕分辨率重烘、3 案 1080p 烘，是两种分辨率混在一起的口径。第二、三轮的封装读数可用（两次自差远小于差值）；第一轮重型抽测的封装读数不可用，全文不引用。

还有两件必须一起看的事：

- **60 fps 上核显域降下来的那两个效果前缀案，到 120 fps 全部反转**（−57% → +5%、−33% → +34%）：成品是按 60 fps 烘的，播放帧率翻倍时成品这一侧涨得比原作还快。所以帧率要按你在 Wallpaper Engine 里的设置来，**不要烘 60 再按 120 播**。
- **本版不要指望保留实时或分层成品省电。** 省不省取决于原作的绘制工作有多少被搬进了视频，不取决于路线名；大部分图层留在实时时，烘焙只是加了一路解码、几乎没减负担。1.0.1 起默认路径的分层布局最多 4 个视频组，设置跑不通时只给出实算通过的替代设置（2–4 组省；6 组已反噬，核显 +106%；9 组封装 +10.9%）。

## 使用

**包里这些文件你都不用管**：`tools.json`、`package.json`、`build-records\`、`SOURCE.md`、`THIRD-PARTY-NOTICES.md`，以及一大堆 `.dll` 和 `.pdb`，都是程序自己运行和开源许可合规要用的，不用打开、不用修改，更不要删。你只需要双击 `WpeBaker.exe`。（`SOURCE.md` 是 GPL 要求的源码获取说明，只有你打算自己重新编译、或者要把这个包转发给别人时才需要看。）

**程序不记住任何设置**：这一版关掉窗口再打开，档位、分辨率、帧率、输出位置等全部回到初始状态；界面语言默认跟随系统，手动切过之后也不记忆。想留住一套设置，用下面的“保存方案”存成 JSON 文件，下次“载入方案”读回来。

启动 `WpeBaker.exe` 时优先从当前登录会话里正在运行的 WPE 定位安装目录，自动填写 assets 和 `projects/myprojects`；未运行时再查 Steam 安装信息。单个活动屏幕的 Scene 会自动填入，多屏可选择目标，也可点击“重新检测”。官方查询没有返回路径时，会使用当前屏幕的已保存设置并注明来源，不把离线屏幕或其他账户的记录自动选进来。

可将一个 Scene 文件夹、JSON 或 PKG 拖入窗口，也可用文件或文件夹选择按钮导入。设好两个选项——动画精度（效率 / 平衡 / 质量，默认平衡）与交互处理（保留 / 固定视角 / 关闭，默认固定视角）——就可以分析，再加入队列。属性从你在 Wallpaper Engine 里给这张壁纸设的值开始（读不到时用壁纸自带的默认值），见下文「壁纸属性」。分辨率与帧率会替你算好并在分析前显示：**帧率取你在 Wallpaper Engine 里设的帧率上限与屏幕刷新率里较小的那个**，不再固定默认 120（原生分辨率下 120 fps 视频在核显上比轻量原作更贵，见「重型与轻型」）；两者都可以手动改，plan 里记下每个值是来自档位、自动检测还是你的覆盖。支持 60/120 FPS、自定义及分数帧率。默认保留视差；调速预算由档位给（效率 5% / 平衡 3% / 质量求改动最小），可以在高级选项里覆盖或关闭。局部接缝修复已经移除，`--local-seam-repair true` 会直接报错（`--local-seam-repair true is no longer supported; source-period encodings are never repaired.`）。

不是 Scene 的输入会在入口被分类拒绝，不进入分析：**视频壁纸与网页壁纸**报"本工具只处理 Scene"并以退出码 1 结束；**预设包**（`project.json` 只有 `dependency`、没有 `file` 也没有 `type`）报 `status=not_applicable`、`kind=preset` 并指出它依赖的作品 id，退出码 **3**——这类条目本身不含素材，要烘的是它依赖的那个 Scene。

原生渲染器读不了作品里的某个素材文件（暂不支持的 3D 模型或纹理）时，运行时观测起不来、分析无法进行，CLI 以退出码 **4** 结束：`--out` 仍会写出一份 `summary.verdict` 为 `tool_limitation` 的结论，逐个点名读不了的文件、解析停下的字段与文件偏移，以及用到它的图层。这是工具的能力缺口，不是对壁纸的判断；`bake` 会拒绝这份结论。完整退出码：0 已写出 plan，1 不是 Scene 壁纸或分析失败，3 预设包，4 工具局限，130 已取消。

“保存方案”可在分析前或修改设置后，将当前作品的属性和生成设置保存为命名 JSON 文件，不包含素材、不启动烘焙。方案保存在原素材文件夹之外。“载入方案”先核对来源内容、属性和设置，再整体恢复；来源路径可以改变，但内容必须匹配。载入后需要重新分析，队列里的已有结果保持原样。

分析报告除路线、视频组、图层清单与一行结论外，还会说明这张值不值得烘：能读到功耗计数器的平台上，这句话来自对原作本身的实测；读不到就明说这台机器测不了。整幅被可取舍的实时元素挡住时，报告列出换到整幅视频所需的最小一组取舍、每项的代价、以及关完之后还剩什么在实时，用 `--exclude-layers` 应用；不列就不关。

默认要求一个整幅不透明视频。分析器沿实际层级、绘制顺序和脚本/着色器输入判定哪些内容必须保持实时；视差效果即使所在图层深度为零，也保留其鼠标依赖。固定关闭且没有外部依赖的组件样式可以省略，隐藏控制器仍保留。音频响应的粒子（发射器/初始化器/算子任一 `audioprocessingmode ≠ 0`）与音频频谱着色器同级，一律留实时。运行时判为"只播一次"的高置信动画轨，其图层也留实时。

仍有遮挡冲突时，程序列出冲突。可以明确选择把独立实时文字/粒子组件移到前景，或简化固定实时文字特效；这两项会改变遮挡或文字外观，默认关闭，并列出实际受影响对象。也可调整场景属性或明确允许分层后重新分析。全幅因视频组多于一个被拒时，只在上面那三条条件全部成立的情况下自动做一次尾组降级，并把被退回的 root、层名与占比写进 `layout_admission_demotion`；不成立就维持拒绝，并给出可直接照抄的 `--retain-live <ids>`。不会静默改属性、关闭视差或退回裁小的透明视频。

烘出来与原作结构同构的场景默认不烘：判成视频外壳时 plan 里有 `video_dominant` 与一条 blocker，`analyze` 仍以退出码 0 结束，但 bake 会在入口拒绝。确认要烘（例如只是想要一段定长循环或重新打包）就在 analyze 阶段加 `--video-shell allow`。

循环只根据源码中的周期公式、动画轨道和视频的精确时基计算，在允许的调速范围内求共同整帧长度。生成默认从原作起点开始；只有走残差掩盖路线时，才会在已锁定的周期内另选一个起点相位（周期本身不变，见下一节）。不通过视频相似度推断周期、寻找起点或挑选有限片段。视频还必须确认播放器的循环方式，并排除脚本控制——脚本控制按解析出的目标层定界，解析不出目标时才退回全场景保守处理，范围记在 `loop.video_control_scope`。缺失的信息不会被当成已知周期。旧版观察所得的循环计划必须重新分析。

**三档预设：效率 / 平衡 / 质量。**同一组分量往往有很多个能闭合的周期，周期越短、需要给分量做的调速越大，两者互相冲突。档位管的是**允许多大的观感改动**，循环长度是求解结果：命令行 `--preset efficiency|balanced|quality`，默认**平衡**；质量档可显式选择，上限 600 秒。**效率**给每个可见分量 5% 的改动预算，并在预算内取最短的循环；**平衡**给 3%；**质量**不给百分比，直接求改动最小的解。长度上限 600 / 600 / 1200 秒只是兜底，2 GiB 体积上限（1080p60 约 1176 秒、alpha 打包 810 秒、4K 558 秒）可能把它压得更短，plan 里写明最后被哪一条限住。三道护栏三档相同、不随预算变：最慢的可见项至少走 3 圈、循环至少 60 秒、可见项改频后峰值速度偏差不超过 0.2 px/s（慢项 0.1 px/s）；都不满足就换下一个 L，全都不行时照旧走未解析路径，不回退成"改动最小"，状态记 `no_multiple_within_budget`。27 案扫描的循环长度中位是效率 146 秒、平衡 200 秒、质量 483 秒，单槽烘完 27 案分别是 8.5 / 10.2 / 22.0 小时。**结论行报的是相位偏移圈数，不是百分比**：3% 档 120 秒循环内相位偏 0.360 圈、5% 档只偏 0.116 圈（短周期项积累更快），改频在一个循环内的相位差恒小于 0.5 圈。1% 这一档换不到东西（4 案在 1% 下无解，中位只缩 1.10 倍），最难的一案在 600 秒内的最小可见改动就是 2.71%，所以低于 2.8% 的预算对它是空头承诺。plan 的 `retime_profile` 记档位、预算、上限与三道护栏的值，`sway_retime` 逐项记预算来源、相位偏移圈数、最慢可见项圈数与峰值速度偏差；换档要重新分析，不能在既有 plan 上改。

**接缝没过不等于立刻放弃：候选回退。**选中候选的编码接缝校验失败时（切口比对放行的不算失败），烘焙按候选表现有顺序把下一个候选换到首位重跑，整张表最多试 3 个候选（`LoopCandidateFallback.MaximumAttempts = 3`）；每轮失败先删掉该轮的 `output/{group-id}` 再进下一轮，磁盘峰值不叠加。每次尝试的帧数、秒数、总调速与每组接缝读数写进 `bake.json` 的 `loop_candidate_attempts[]`，最终选中的写 `selected_loop_candidate`；三个都失败仍是 `candidate_rejected_seam`，拒绝理由里逐条列出试过的候选。回退只换候选，不放宽任何阈值。

解析周期不完整时，程序可尝试一次更小的烘焙分配：将未解决机制及粒子所在的完整作者子树保留实时，再重新检查周期和构图。若没有剩余可烘焙内容则停止。有明确源静态证据的图层可直接生成静态纹理。图像检查只验证既定方案；不做任何局部接缝修补，周期和起点不会被事后改写。

analyze 自己也会把这条回退走一遍并留证：整层路线在没有 blocker 却求不出循环时，计划里的 `loop_allocation_fallback` 记下保留了哪些作者根、重新分析后的路线与候选数；能走通就在 `loop.unresolved` 里给出 `--retain-live <ids>` 这条出路，走不通就写明原因。analyze 本身不替用户改分配。任何 `whole_layer.status=unavailable` 的结局都必须在 `whole_layer.blockers` 或 `loop.unresolved` 里至少留下一条理由，否则视为内部错误直接报错——零理由的“成功”退出比报错更难处理。候选为空时另有 `loop.no_candidate_reason` 给出结构化原因，顶层 `suitability` 给出一句裁定。

要不要烘由用户决定，程序不用绘制时间估算当门卫：分析不跑成本探针，也不会因为成本拒绝任何方案。视频外壳判据是唯一的"默认不烘"，它判的是结构同构而不是估算收益，且有显式覆盖开关。能形成单一不透明整幅组就整幅；否则按已选的 `--live-overlays foreground` 或 `--video-layout layered` 处理，两者都没选时在计划里报“需要选择”并列出冲突的实时层。`analysis_device` 仍记录本次分析用的设备名、UUID、Vulkan 设备类型和类别，只作溯源。`wpe-baker cost-probe` 作为可选诊断保留，只测量、不裁决；最终收益需在目标机器上比较原场景与成品。

分析结论有中英两份：plan 里 `blockers_localized`、`loop.unresolved_localized` 与顶层 `summary` 并列给出中英文案与 key，命令行 `--lang zh|en` 选语言（不传按系统界面语言猜），analyze 结束在 stderr 打一行结论，stdout 仍是纯 JSON。`blockers` 数组与 `loop.unresolved[].detail` 里的英文原文逐字未变，按字符串匹配这些文案的旧脚本不受影响。界面语言在窗口右上角切换，默认跟随系统语言；这一版不记忆手动切换的结果，关掉重开会回到系统语言。命令行的 `--lang zh|en` 只管结论那一行。

GUI 的烘焙中间文件在 `%LOCALAPPDATA%\WpeBaker\work`，分析临时文件在 `%TEMP%\WpeBaker\analysis-<guid>`，日志在 `%LOCALAPPDATA%\WpeBaker\Logs`。一次烘焙**正常跑完**时，内部 raw、PCM、master 和 partial 媒体会在最后一个使用阶段结束后清理，写入前后都会检查剩余空间；但**中途关窗口、取消或崩溃时 work 目录不会自动清理**，需要自己删（见「卸载与清理」）。无损 master 体积很大，几次中断就可能占掉几十 GB。分析临时目录由程序在每次启动时自动清掉超过 7 天的那些。成功生成后，干净项目直接写入所选保存位置的独立子目录，其根目录包含 `project.json` 和 `bake.json`，默认可被 WPE 的本地项目库识别。失败或取消不向图库写入成品，已有项目不会覆盖。`bake.json` 保存图层、循环、合成、编码和硬解记录，可重新载入；修改生成条件需要重新分析，重跑使用新目录。CLI 的既有 `--out/project` 布局仍兼容；JSON 请求可用 `project_directory` 指定独立成品目录。

烘焙速度已移除无下游用途的逐帧全幅 FNV 计算，保留帧号、PTS、像素一致性和最终 SHA256 检查。同机120帧4K测试的实际捕获、无损编码及校验耗时平均8.966→4.925秒；这不代表最终HEVC编码或整段接缝修复也提速同样比例。两者仍可能占据较长时间。

每次烘焙都记分阶段计时：`bake.json` 顶层 `stage_timing` 按互斥阶段记秒数——`source_capture`、`composition_validation`、`loop_start_search`、`master_render`、`seam_check`、`crossfade`、`encode_playback`、`encode_quality_check`、`hardware_decode_check`、`project_assembly`、`other`，相加等于 `total_seconds`；**没发生的阶段写 `null` 而不是 0**。`master_render_breakdown` 另记与渲染重叠的 `readback`、`encode_master`、`renderer_wall_seconds`，不参与求和。例如绫波丽那次 90.640 秒里主渲染 45.154 秒、成品编码 13.247 秒、编码质量校验 23.111 秒、画面对照 5.731 秒。`effect_prefix` 路线下 `stage_timing.frames` 目前仍写 0、`frames_per_second_render` 为 null，这条路线上拿不到每帧口径。

用官方播放预览检查画面。内建检查报告可直接查看；“测量当前播放”只读当前 WPE 进程，不自动切换壁纸或启动测试窗口。Windows 显示帧跟踪需要管理员权限。显示 FPS 与 API 提交节奏分开记录；权限不足、缺失或多交换链数据按原状态保留，采样不自动判定节能。比较收益时需要同画面、同帧率和受控后台负载的来源/成品对照。

导出生成项目的 ZIP，或选择一个明确屏幕后应用。恢复通过该次 `apply.json` 记录的程序和屏幕执行；发现用户后来换了壁纸就停止恢复。原来源保留，派生的 WPE shader 缓存不计入来源指纹。

**成品在哪、怎么放到桌面上、怎么还原**

没装 Wallpaper Engine 时，成品默认写在 **`我的文档\WPE Baker`**；装了的话，保存位置会自动预填成 Wallpaper Engine 的 **`projects\myprojects`**，这样成品会直接出现在它的本地壁纸库里。两种情况下都是一张壁纸一个独立子目录，里面有 `project.json` 和 `bake.json`；保存位置可以在界面上改。

放到桌面上有两条路：在本工具里选一块屏幕点“应用”；或者打开 Wallpaper Engine →“从文件安装/打开壁纸”→ 选成品目录里的 `project.json`，之后照常双击应用。

**还原**：点“回滚”，程序按这次应用时记下的 `apply.json` 把那块屏幕换回原来的壁纸；没有对应记录时可以用“从文件回滚”手动选一个 `apply.json`。命令行是 `wpe-baker rollback APPLY.json --wallpaper-engine EXE`。如果中途你自己在 Wallpaper Engine 里换过壁纸，回滚会主动停下不动你当前的选择——这时直接在 Wallpaper Engine 里选回原来那张即可。本工具从不修改、覆盖或删除你订阅的原壁纸，成品是另存的一份。

命令行：

```
wpe-baker --help
wpe-baker analyze --help
wpe-baker analyze SOURCE --out PLAN.json
wpe-baker analyze SOURCE --preset quality --out PLAN.json
wpe-baker analyze SOURCE --fps 60 --fps-den 1 --lang zh --out PLAN.json
wpe-baker analyze SOURCE --video-shell allow --out PLAN.json
wpe-baker analyze SOURCE --exclude-layers 224,269,2242 --out PLAN.json
wpe-baker bake PLAN.json --out NEW_DIRECTORY
wpe-baker measure-official REQUEST.json
```

请求路径相对工作目录，工具路径相对 `tools.json`；保留分析工作目录直到生成结束。

analyze 里会改变计划内容的参数：

- `--preset efficiency|balanced|quality`：允许多大的观感改动（5% / 3% / 求改动最小），默认 balanced；质量档上限 600 秒，plan 的 `preset_applied` 记实际档位。高级覆盖是 `--retime-budget PERCENT`（0..5）与 `--loop-max-seconds`；旧名 `--loop-preference`、`--max-retime`、`--loop-length-max` 保留一个版本作别名并提示改名。
- `--interaction keep|fixed|off`：由输入驱动的内容怎么处理——保留实时、固定视角（默认）、或再去掉指针效果与采样成本高的大面积音频效果。时钟、日期、媒体文字在任何模式下都保留实时。
- `--keep-live on|off`：`on` 完全走 1.0 的分析路径（平衡档、保留视角、不给建议、不加新字段），即界面里的兼容模式；不能与 `--interaction` 同用。
- `--measure-source on|off`：分析前在官方播放器里实测原作功耗，默认关。
- `--sway-retime on|off`：摆动改频**默认开**，三档都开——档位的观感预算管的就是它。要关掉才显式传 `--sway-retime off`（界面上在「高级：调速覆盖」里取消「摆动改频」），关掉后摆动分量按未解析处理，只会多出拒绝。
- `--fps N --fps-den D`：覆盖自动算出的帧率，plan 里该值记为手动覆盖而不是自动。
- `--properties-source wpe|defaults`：属性从哪里起步。`wpe`（默认）读你在 Wallpaper Engine 里给这张壁纸设的值；`defaults` 用壁纸 `project.json` 里的默认值（见「壁纸属性」）。
- `--properties PROPS.json`：一个"属性名 → 值"的 JSON 对象，覆盖在上面的起点之上。
- `--exclude-layers ID,ID`：把列出的图层及其子树按"在原作里关掉"处理，不进视频、不留实时、也不生成静态纹理。ID 取自 plan 的 `layers` 列表；场景里没有的 ID 直接报错。不列就不排除。

## 壁纸属性

壁纸自带的可选元素——赞助码、署名、时钟、媒体信息、镜头雨痕等——由这张壁纸自己的属性开关控制，和在 Wallpaper Engine 里一样。**烘焙默认沿用你在 Wallpaper Engine 里给这张壁纸设的属性值**，烘出来的成品就是你桌面上看到的样子。Wallpaper Engine 把这些值按壁纸存在安装目录 `config.json` 的 `<用户名>.wproperties` 下，WPE Baker 只读这个文件、从不写入。查找顺序：正在运行的 `wallpaper64.exe` 所在目录 → 按注册表和 Steam 库推导出的安装目录 → GUI 设置里的 Wallpaper Engine 路径（CLI 用 `--assets` 的上一级）。每个值都按 `project.json` 里的属性类型核对（开关、滑块范围、下拉选项、颜色、文字），不合法的值和 Wallpaper Engine 自己的显示设置（对齐、调色等）会被忽略并列在 plan 里。

优先级：壁纸默认值 < 你在 Wallpaper Engine 里的值 < `--properties`（GUI 里是属性面板上的改动；面板上取自 Wallpaper Engine 的项标有"来自 WPE 设置"）。`--properties-source defaults` 跳过 Wallpaper Engine 的值。

以下情况回退到壁纸默认值，并在 plan 和一行结论里写明：找不到或读不了 `config.json`；`config.json` 里有多个用户，又没有恰好一个对得上当前 Windows 用户或 Steam 登录账户；这张壁纸在几块屏幕上的设置不同，又分不出正在哪块屏幕上放。在 Wallpaper Engine 里没改过属性的壁纸照默认值烘，plan 除两个来源字段外和以前一样。

plan 里记 `properties_source`（`wpe` / `defaults` / `wpe_unavailable`）和 `wpe_properties`（原因、用的哪个 `config.json`、用户、记录键、屏幕、生效的键、与默认不同的键、被覆盖的键、被忽略的值）；实际用到的值在 `snapshot_properties` 里并带进 bake。已在阿米娅 3486806915 上只跑 analyze 核对过：用户在 Wallpaper Engine 里改过 9 个属性（8 个开关关掉、1 个滑块）；默认情况下 9 个全部生效，实时层从 21 个降到 14 个，与用 `--properties` 传入同样的值结果一致；加 `--properties-source defaults` 回到 21 个。画在素材本身里的内容没有开关可关，会原样留在成品里。

## 卸载与清理

绿色便携版，没有安装程序。删掉解压出来的那个文件夹，程序本体就没了。它运行时会往下面三个地方写东西：

- `%LOCALAPPDATA%\WpeBaker\work` —— 烘焙工作目录（最占地方，中间的无损 master 就在这里）
- `%LOCALAPPDATA%\WpeBaker\Logs` —— 运行日志
- `%TEMP%\WpeBaker\analysis-<随机字符>` —— 每次分析的临时文件（程序每次启动会自动清掉超过 7 天的）

烘焙工作目录和日志不会自动清理，卸载时请一并删掉：

```powershell
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\WpeBaker", "$env:TEMP\WpeBaker"
```

**成品不会被删掉**：`我的文档\WPE Baker`（或你指定的输出目录）里已烘好的壁纸要不要留由你决定，删了不影响 Wallpaper Engine 里你订阅的原壁纸。如果某个成品正应用在桌面上，先换回别的壁纸再删。

## 解析周期 + 残差掩盖

一句话版本：**周期锁死在从源码解出来的那个数上，绝不挪动；只有少数被证明非周期、且幅度有界的图层，才允许用接缝处 0.4 秒（60 fps 下 24 帧）的整帧交叉淡化摊开。** 裁决只有一层，实测值和阈值都会原样写进 `plan.json` 与 `bake.json`：淡化窗口内每一帧的残差 Δ_k = f[P+k] − f[k] 取最差 64px 瓦片，最大值 ≤ 48/255，且硬切残差 Δ_0 的整幅 RGB MAE ≤ 2/255——淡化后看得见的重影和接缝附加步进都由它决定，与场景普通运动快慢无关。淡化之后另有一道实现自检（不是可调判据），超出推导上界就按内部错误停下。每个视频组还会导出 `seam-preview.mp4`（接缝被拒时同样导出），把循环末尾 N 帧接开头 N 帧、原速加 0.25 倍速各放一遍并标出帧号，可以直接肉眼复核。阿米娅 3486806915 是目前走通这条路线的成品：6000 帧、单组、接缝校验通过，24 帧淡化窗口里真正重编码的只有 24 帧，其余 5976 帧原样流复制。**但这条路线到目前为止只在阿米娅这一张壁纸上实证过。** 另外三个形态合适的候选（Hacker 3019043758、3470764447、3326873240）都在更早一环的布局准入就被拒，没有产生任何残差掩盖数值，所以这条规则的通用性还没有第二个样本。

循环周期只从源码解析得来：着色器时间方程、动画轨道速率、脚本时长。相似度搜周期、盲搜长周期、把首尾拼接
冒充周期，一律不做。解析没有候选就直接拒绝，并在 `loop.no_candidate_reason` 里写明是哪一类无解。

有些源场景在解析出周期之后仍剩下少数未解析分量。这时只有**已被证明是随机的**分量才允许被接缝处的交叉淡化掩盖：

1. **脚本随机重启的精灵**：脚本在同一段代码里取到该精灵动画、做播放控制并用 `Math.random()` 喂定时器延迟重启。
   同一 owner 下被脚本控制的骨骼/属性动画轨道不借用精灵的随机证明。
2. **满足平稳随机判据的粒子系统**：读 analyze 写在 `loop.unresolved[].particle_stationarity` 里的 C1–C9 结论
   （发射率恒定、标记独立随机抽取、算子只依赖年龄与平稳噪声场、没有外部输入），不按定义里有没有 random 字样判断。
   判据不通过或旧版计划没有这个字段的粒子层不可掩盖；通过的粒子层带出预热时长，起点搜索与 master 都先跑过
   所有被烘粒子层预热的最大值（`particle_warmup_frames`）。

**位移类分量不可掩盖**：foliagesway 这类着色器 UV/顶点抖动（`bounded_displacement`）即使幅度有界，淡化后也是同一元素在
接缝两侧位置不同的半透明双影，人眼定标判定明显，所以一律阻断——只能解析闭合它的周期，或把这一层保留实时。能算出的峰值
偏移照样记下，只作取证。`UnsupportedShaderMechanism` 这种"没有规则匹配"的分量不算证明，照旧阻断。
随机精灵与粒子的**画布占比只记录、不裁决**：每层的 `canvas_fraction`（层包围盒占场景画布的比例，
算不出时为 null）与合计 `sprite_canvas_coverage_total` 都写进 plan/bake.json 供核对，但包围盒对
带透明边的精灵图集会高估几十倍，用它当门卫没有意义——掩盖是否可接受由下面全分辨率的第一层残差判据实测决定。

条件满足时，在锁定的解析周期 P 内挑选起点相位：采集 2 个周期的降采样样本（窗口固定 2P——候选起点只有
P/步长 个，每个比较的是 (s, s+P)，全部落在前 2P 帧里，更宽的窗口不会引入新候选；采样步长取 gcd(P, 16)，
周期不是 16 的倍数时步长自动缩小），对每个候选起点算接缝残差。起点在第一个含残差层的视频组上搜，**共享给所有组**，
组间相位关系与原作一致。**周期不因此改变，只决定相位。**随后在每个含残差层的组的全分辨率无损 master 上复核：

- **第一层（唯一裁决）**：淡化窗口内每个 k∈[0,C) 的残差 Δ_k = f[P+k] − f[k] 取最差 64px 瓦片 RGB MAE，
  **最大值 ≤ 48/255**，且硬切残差 Δ_0 的**整幅 RGB MAE ≤ 2/255**。淡化之后观众能看到的只剩三样，全由 |Δ_k| 决定：
  重影峰值 min(w,1−w)·|Δ_k| ≤ 24/255；接缝那一步比原作多出 |Δ_0|/(C+1) ≤ 1.92/255；淡化段每一步多出
  ≤ |Δ|/(C+1) + ½·|Δ_k − Δ_{k−1}|。它们与场景普通帧间步进的快慢无关，所以不再和普通步进 p95 比。
  48 与 2 是残差掩盖仅有的两个需要人眼定标的数。`bake.json` 的 `seam_residual.first_layer` 记最大瓦片值、
  出现在哪个 k、Δ_0 的整幅与最差瓦片、每个 k 的读数，以及只记录不裁决的重影峰值估计 `ghost_peak_worst_tile_rgb_mae_255`。
  透明组的 master 左半是预乘色、右半是覆盖度，两半分别算：覆盖度半单通道；预乘色半只统计任一帧覆盖度 > 0 或 RGB 非零
  （加性粒子不写覆盖度）的像素，瓦片分母仍是全部像素；第一层取两半里更大的读数（`packed_measurement`）。
- **淡化实现自检（原第二层，不是判据）**：淡化做完后解出原 master 的 f[0..C]、f[P−1..P+C−1] 与成品 g[0..C]，
  对每一步核恒等式——成品相对原作参照步进多出的量，逐瓦片不得超过由 Δ_k 推导的上界加 1/255 取整余量。
  超出说明淡化的权重、混入帧或拼接错了，按内部错误抛出；结果记在 `loop_crossfade.step_self_check`。

起点排序键是样本上能看到的第一层量 max(Δ_0, Δ_stride)（stride 不在淡化窗口内时只有 Δ_0）：先准入
（样本整幅 ≤ 2/255），再按排序键从小到大排。排序键是降采样估算，看不到淡化窗口后段的单帧尖峰，所以只用来排序、不做准入。
全分辨率第一层在某个起点上被拒时，按这个排序依次换下一个候选起点、重渲 master 再测，最多 8 个；全部被拒才拒绝。
每次尝试的起点、样本排序键与各残差组的 max_k / 整幅读数记在 `bake.json` 的 `loop_start_attempts`，最终用的起点记在 `selected_loop_start`。

通过后，每个含残差层的组在接缝处做整帧线性交叉淡化，窗口固定 0.4 秒（60 fps 下 24 帧）：
`out[i] = (1-w)·f[i] + w·f[P+i]`，`w = (C-i)/(C+1)`。周期分量在两端逐像素相同，混合后不变；只有残差
分量被摊开在这段窗口里。透明组在左右并排的 packed 图上用同一个公式：合成 out = C + (1−α)·B 对预乘色 C 与覆盖度 α
是线性的，packed 域线性混合就是预乘空间里正确的淡化，任何背景下都不偏色。**不做任何局部接缝修复。**

组数与透明与否都不限；布局淡化不了的只有"可掩盖分量所在的图层不在任何视频组里"，这时 analyze 写 blocker、bake 干净拒绝。
`bake.json` 与 plan 会记下
`seam_policy = "analytic_period_with_residual_masking"`、每个残差层的机制与证明摘要、占比、含残差层的组（`residual_group_ids`）、
预热帧数、搜索窗（几个周期）与候选数、选中的起点帧、第一层的实测值（顶层 `seam_residual` 是读数最差的组，每组自己的读数与
`loop_crossfade` 在组记录里）、淡化自检读数与阈值、`crossfade_frames`。每个视频组的接缝校验一结束（通过、被拒、与原作切口一致都算）就在组目录下导出
`seam-preview.mp4`：循环末尾 N 帧接开头 N 帧（N 与淡化窗口一致，60 fps 下 24 帧），原速一遍再 0.25 倍速一遍，
顶部标签条写循环帧号，末尾段红底、开头段绿底，颜色切换处就是接缝。只按时间段 seek 解码这 2N 帧；
`bake.json` 每组的 `seam_preview` 记路径，导出失败只记 warning、不影响结论。任何拒绝都会写明是哪一层、哪个机制、缺什么证明或超了哪个阈值。

## 与原作切口一致即通过

有些源片自己首尾就不接：周期解得对，成品也如实复现了源片那道口子，接缝校验却把它算成烘焙缺陷。RC6 加了一条只在**源周期路线**上生效的补充判据：接缝校验判 `observed_seam_fail` 之后，再问一句"这道口子是不是素材自己就有的"——解码片源自身的最后一个内容帧与第一个内容帧，按候选**同一套瓦片网格**算它自己的环绕残差，逐块对照。三条全过才放行：① 接缝校验标记过的每一块，候选残差 ≤ 源自身残差 × 1.15 + 1/255；② 标记集合之外没有任何一块够到绝对瓦片门槛（门槛从接缝报告自己的 `thresholds` 读，不另立数）；③ 整幅逐瓦片残差图与源片的 Pearson `r ≥ 0.95`。通过则 `loop_validation = encoded_seams_match_source_discontinuity`，否则维持原拒绝并把比对读数追加进 `reason`。

适用条件很窄，任一不成立就不走这条路、原因原样写进 `bake.json`：解析周期完全来自视频轨且只由那一条 `video/…` 分量承载、该层独占整幅未裁剪的居中捕获、计划只有一个视频组、组内只有一层、非 packed alpha、候选没有重定速补丁、整幅接缝与整幅运动本身都还在预算内。**shader / 动画周期主导的场景永远不适用**——它们的接缝理论上应为零，必须自己闭合；残差掩盖路线走自己的判据，这条规则一行没碰它。注意这条判据放行的形态，正是 RC8 的视频外壳判据默认拦下的形态：两者不矛盾——接缝可以如实复现，但"要不要烘一个与原作结构同构的东西"是另一个问题，交给用户用 `--video-shell allow` 回答。

配套的**内容节拍校准**（`content_cadence`）修正另一类误判：30 fps 素材在 60 fps 捕获下每帧成对重复，旧口径把这种重复帧当成一次"普通步进"，把正常步进的统计压低。改成按一个*内容*帧测步进后，DJGun 3754908581 的误判瓦片从 56 降到 6、`velocity_outlier` 归零；剩下 6 块正是源片自己在第 899→0 帧的切口（源自身最差瓦片 22.7708、候选同块 23.0339、容差线 26.1904，整幅 2040 块 `r = 0.993869`），于是这一案按上面的规则通过。

## 裁减范围

已移除旧版局部光效/静态效果缓存及其特例配方、Video/Web 媒体压缩、独立原始视频/效果补丁导出、重复离线预览、离线性能基准和自动弹窗 A/B 测试。旧 v1 actions 请求与媒体优化计划不再支持，需重新分析 Scene 来源。只读官方采样、原生诊断和现代生成链使用的画面/接缝校验保留。

生成仍使用 BT.709 SDR H.264/HEVC，按尺寸和帧率选择兼容编码；每个完整视频做一次硬解短检，**验的是烘焙这台机器**，结果里现在写明了这一点：`verified_on` 逐张列出适配器的厂商与核显/独显分类，`target_caveat` 标明该结论只覆盖烘焙机。在独显上烘、到核显上播的，把成品拷过去跑一次 `wpe-baker decode-check`。另有一条厂商无关的保守提示：H.264 宽或高超过 4096、HEVC 超过 8192×4320 或亮度样本数超过 33,177,600 时，提示多数核显可能解不动。短检不能替代持续官方播放或整体收益验证。AV1 仅有独立解码检查，未加入生成；透视、部分脚本/木偶及不规则动画仍可能被拒绝或存在兼容缺口。HDR 不再被标志本身一刀切拒绝，但要通过逐层 SDR 辐射闭合证明；证明不了就仍然拒绝，并点名是哪一层哪条判据。

成品编码的硬件通道只走厂商无关的那一条，而且在这一版上仍然落到软件：`wpe-baker bake --encoder software|mf|auto`（GUI 同名下拉），默认 `software`，只作用于成品编码，**无损 master 永远是软件 `libx264rgb` 无损**。包内 GPL2 ffmpeg 的编码器白名单是 `libx264 / libx264rgb / libx265 / h264_mf / hevc_mf / av1_mf / aac / pcm_* / rawvideo`，**里面没有 nvenc、qsv、amf**，所以 `--encoder nvenc` 之类的请求会回退软件并把原因写进 `bake.json`（历史上 34 个案的 `requested` 全是 software）。厂商无关的通道是 Windows Media Foundation（`h264_mf` / `hevc_mf`），选它是因为目标播放设备是核显。但它在我们的机器上只能落到微软自带的软件 MFT：上游 ffmpeg 只在编码第一帧 D3D11 画面时才绑定 D3D manager，而厂商 MFT 在更早的 `SetOutputType` 就要求绑好，于是硬件 MFT 能被枚举到、随后以 `MF_E_UNSUPPORTED_D3D_TYPE` 拒绝；换全功能版 ffmpeg 一模一样地失败，所以这不是包内构建缺选项。`bake.json` 如实写 `mf_hardware: false` 与原因，不把它当硬件编码。顶层 `playback_encoder` 与每组 `playback_encode` 仍记 requested / used / 回退理由 / 耗时 / 完整命令行。D3D12 Video Encode（`h264_d3d12va` / `hevc_d3d12va`）实测在 AMD 核显上能编，是下一步，不是本版已有功能。

## 已知问题

- **无 AVX2 的机器上，读端帧扫描没有性能数据**：扫描只在 9800X3D（AVX2 / AVX-512）上实测过；不支持 AVX2 的 CPU 会走标量回退路径，该路径的逻辑有单测覆盖（行宽小于 8 像素的尺寸走的就是它），但**性能未测**，耗时可能明显高于本文给出的数字。
- **保留实时与分层成品通常比原作更费**（实测 8 案里 5 案，封装 +8% ~ +23%）：实时层的开销原样保留，又多了一路视频解码。1.0.1 起默认路径的分层布局最多 4 个视频组；超过就按替代设置实算，通过才建议。
- **实验性：时段壁纸状态拆分**（`--daytime-split on`，仅命令行，默认关闭）。时钟脚本只切换图层可见性的场景，会按时段拆成若干状态，每个状态单独分析、单独烘焙，原脚本保留。试过的三案里两案识别成功；剩余实时层仍决定该状态能否变成整幅视频。开关关闭时 plan 与上一版逐字节相同。
- **取舍方案在烘制阶段可能仍然失败**：取舍清单是分析阶段的判定，烘制第一步的循环分配会重新判定；粒子系统或主体动画层没有周期时会被改判为保留实时，整幅所需的"一组不透明视频"不再成立，于是烘制被拒。23 案复验全部如此，0 案烘出成品。清单给的是可以一试的方向，不是能烘成的承诺。
- **`--exclude-layers` 指向必须实时的层时会被静默忽略**：把那些必须保持实时的层（粒子系统、无周期的主体动画）写进 `--exclude-layers`，plan 回显的排除集里不会有它们，命令行既不报错也不提示，拒因也不会变。后续版本改为报错。
- **硬解短检只覆盖烘焙这台机器**：每个完整视频的硬件解码短检验的是当前烘焙机，结果里 `verified_on` 逐张列出适配器的厂商与核显/独显分类，`target_caveat` 标明结论只覆盖烘焙机。在独显上烘、到核显上播的，请把成品拷到目标机跑一次 `wpe-baker decode-check`；短检也不能替代持续官方播放或整体收益验证。

## 开发

本机跑长烘焙统一走 `scripts/run-guarded.ps1`：它盯着系统可用内存与目标盘剩余空间，任一越线立刻终止整棵进程树并把原因写进 status 文件。看门狗自身出错时（资源采样连续失败、status 文件被占用等）同样会先杀掉整棵子进程树，再把 status 写成 `watchdog_failed` 和原因，不会留下无人看管的子进程；单次采样失败只沿用上一次的值并计数，连续 `-MaximumSampleFailures`（默认 4）次才判定保护失效。数组参数要用 `& scripts\run-guarded.ps1 -Executable ... -Arguments @('a','b')` 调用，`pwsh -File` 会把数组拍平（脚本会检出这种畸形入参直接报错）。不要用 `Invoke-CimMethod Win32_Process Create` 拉 MSIX（Microsoft Store）版 pwsh：那样起来的进程落在 Session 0 会静默退出，日志和 status 一个字都不写；计划任务或远程拉起请用 `powershell.exe` 或非 MSIX 安装的 `pwsh.exe`。

开发者可使用项目内的 Python 辅助脚本下载和构建，普通用户不需要此环境。原生渲染器的源码是 `engine/`：`waywallen/open-wallpaper-engine` 的 GPL-2.0 分叉，上游基点 `b866e8e711fdd7762385b23601affa1ea5539e3b`，带完整 Git 历史，Windows 改动就是其中的普通提交。

```text
python scripts/fetch-dotnet.py
python scripts/build-managed.py src/Baker.Cli/Baker.Cli.csproj
python scripts/build-managed.py src/Baker.App/Baker.App.csproj
python scripts/build-native-cmake.py --target wpe-render --toolchain .tools/llvm-mingw-22 --build-dir build/native-speed22 --ffmpeg-root .deps/ffmpeg-lgpl21/prefix
python scripts/package-portable.py --native-build-dir build/native-speed22 --out dist/preview-LOCAL
python scripts/package-source.py --native-build-dir build/native-speed22 --output dist/WpeBaker-source-LOCAL.zip
```

两项打包命令必须使用同一个 `--native-build-dir`。它指向包含 `bin/wpe-render.exe` 和
`provenance/build-wpe-render.json` 的已验证原生构建目录；脚本会拒绝渲染器哈希、来源快照或 provenance
不一致的组合。可选的 `package-portable.py --acceptance-report PATH` 只复制并链接已有验收记录，不会把
`not_verified` 改写成已验证。

`build/native-release22` 是 2026-09-09 的旧渲染器构建，仅作历史留存，不要用于打包；它的溯源记录里
`binary.path` 指向另一个构建目录，用它当默认值会被 `load_verified_build` 拒绝。本次发布的多线程渲染器在
`build/native-mt22`，两条打包命令都要显式写 `--native-build-dir build/native-mt22`。

打包前不要让 Git 重写工作树。源码绑定逐字节校验全部源码文件，其中 6 个是被跟踪的脚本
（`build-ffmpeg-lgpl21.py`、`build-native-cmake.py`、`distribution-inputs.lock.json`、
`fetch-ffmpeg-lgpl21-inputs.py`、`native-inputs.lock.json`、`native-provenance.py`）。在
`core.autocrlf=true` 且没有 `.gitattributes` 覆盖它们的机器上，这些文件在工作树里是 LF
（`native-inputs.lock.json` 还是混合换行），一旦被 Git 重写就会变成 CRLF、绑定立刻失效。切换分支请用
`git fetch <bundle> <分支>:<分支>` + `git switch`，别对 `scripts/` 用 `checkout -f`、`reset --hard`、
`stash` 或 `clean -x`；确实要还原某个文件时只还原那一个路径，不要整树还原。

测试跑法是 `dotnet test tests/Baker.Core.Tests -c Release`（xUnit）。`--filter "Layer!=L3"` 只跑不需要 ffmpeg、渲染器、GPU 或本机夹具的 L0–L2；L3 的工具路径取 `tools.json` 或 `WPE_BAKER_TOOLS_JSON`，缺了就跳过并写明原因。

原生依赖、输入版本、对应源码和完整构建说明见 `scripts/NATIVE-BUILD-STATE.md`、`scripts/DISTRIBUTION-DEPENDENCIES.md` 及输入 lock 文件。合成测试素材在 `tests/`。真实 Workshop 素材和生成文件放在忽略的 `artifacts/`，不进入公开源码包。
